# Запас

Система учёта остатков, сроков годности и стоп-листов для общепита и розницы. Показывает, что и где лежит, что испортится раньше, чем его купят, какие позиции и блюда нельзя продавать прямо сейчас, и подсказывает, что делать: списать, уценить, переместить, продвинуть через блюда или заказать.

Решение сделано для хакатона UmirHack III (кейс «Мониторинг остатков, сроков годности и стоп-листов»).

## Что умеет

- **Партионный учёт.** Каждая поставка это партия со своим сроком и себестоимостью. Расход идёт по принципу «первым уходит то, что раньше испортится».
- **Операции:** приход, продажа, списание, перемещение между точками, инвентаризация. Каждая создаёт документ и неизменяемые движения.
- **Заказы поставщикам.** Расчёт, что и сколько заказать (по остаткам, продажам, сроку поставки и уже заказанному), черновики, отправка письмом и событием, приход по заказу.
- **Интеграции.** Изменения стоп-листа уходят в доставку, кассу или любой сервис вебхуками с подписью и повторами, кассе доступна лента стоп-листа и каталога по ключу, номенклатура загружается из CSV-выгрузки iiko и 1С.
- **Прослеживаемость.** Номер ВСД («Меркурий») и коды маркировки («Честный знак») записываются при приходе, система напоминает о сроке погашения.
- **Блюда и рецептуры.** При продаже блюда ингредиенты списываются сами.
- **Стоп-лист.** Автоматический (нет остатка, весь остаток просрочен, не хватает ингредиента) и ручной, с причиной и временем начала.
- **Прогноз и рекомендации.** Скорость продаж за четыре недели, расчёт, сколько из каждой партии не успеют продать, и конкретные действия с суммами.
- **Панель руководителя:** деньги под угрозой, просрочка, остатки по срокам, списания за 30 дней.
- **Роли и точки.** Администратор, менеджер, кладовщик, наблюдатель. Кладовщик и наблюдатель видят только свои точки.
- **Интеграции:** продажи с кассы по API-ключу, сводки и стоп-лист в Telegram, выгрузки в CSV для Excel.
- **Журнал аудита** с цепочкой контрольных сумм: подмену записей видно.

Подробности: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), [docs/SECURITY.md](docs/SECURITY.md), [docs/API.md](docs/API.md).

## Быстрый запуск в Docker

Нужны Docker и Docker Compose.

```bash
cp .env.example .env
# впишите в .env пароли и JWT_SECRET (команды для генерации подсказаны в файле)
docker compose up -d --build
docker compose --profile demo run --rm seed             # демо-данные за 60 дней
# или, для рабочей установки без демо-данных, первый администратор:
docker compose --profile admin run --rm create-admin    # спросит почту, имя и пароль
```

Проверено на Docker 29 и Compose 2.40: сборка образа, миграции при старте, `create-admin`, загрузка демо-данных, проверка здоровья.

Приложение откроется на http://localhost:3000 (порт задаёт `APP_PORT`). Порт слушает только локальный интерфейс. Для доступа из сети поставьте перед приложением обратный прокси с HTTPS и задайте `TRUST_PROXY=1` (число прыжков до приложения). Значение `true` доверяет любому заголовку `X-Forwarded-For`, и клиент сможет подделать свой адрес.

Если проверяете по обычному http не на localhost (например, по адресу в локальной сети), задайте `COOKIE_SECURE=false`: браузер не принимает защищённые cookie по голому http.

## Запуск для разработки

Нужны Node.js 22+ и PostgreSQL 15+.

```bash
npm install

# база и роли (один раз)
psql -U postgres <<'SQL'
CREATE ROLE zapas_owner LOGIN PASSWORD 'придумайте';
CREATE ROLE zapas_app   LOGIN PASSWORD 'придумайте';
CREATE DATABASE zapas OWNER zapas_owner;
REVOKE ALL ON DATABASE zapas FROM PUBLIC;
GRANT CONNECT ON DATABASE zapas TO zapas_app;
SQL

cp apps/server/.env.example apps/server/.env    # впишите пароли и JWT_SECRET
npm run migrate
npm run seed                                     # демо-данные; для чистой базы вместо этого: npm run create-admin -w @zapas/server
npm run dev                                      # API на :3000, интерфейс на :5173
```

Интерфейс разработки: http://localhost:5173 (запросы к `/api` проксируются на сервер).

Сборка и запуск как в продакшене:

```bash
npm run build
WEB_DIST=../web/dist NODE_ENV=production npm run start   # путь относительно apps/server
```

## Подключение кассы

Администратор выпускает ключ в разделе «Администрирование → Ключи кассы». Ключ привязан к одной точке и умеет только отправлять продажи.

```bash
curl -X POST http://localhost:3000/api/pos/sales \
  -H 'X-Api-Key: zk_...' \
  -H 'Content-Type: application/json' \
  -d '{"externalId":"чек-2026-10-08-0001","lines":[{"productId":"<id>","quantity":2}]}'
```

Повторная отправка с тем же `externalId` не спишет остатки второй раз.

## Первый администратор

На пустой базе войти нельзя, а загрузка демо-данных в production отказывает, поэтому учётную запись заводят командой (из `apps/server`):

```bash
npm run create-admin        # спросит почту, имя и пароль (пароль при вводе не виден)
```

Для автоматизации задайте `ADMIN_EMAIL`, `ADMIN_NAME` и `ADMIN_PASSWORD` в окружении. Пароль проверяется по тем же правилам, что и в интерфейсе. Остальных пользователей администратор заводит в разделе «Администрирование».

## Сканер штрихкодов и работа без связи

Кнопка «Сканировать» есть в приходе, продаже, списании, перемещении и инвентаризации.

- **Что читает.** Обычные штрихкоды (EAN-13, EAN-8, UPC, Code 128), QR и коды «Честного знака» (GS1 DataMatrix). Из кода берутся GTIN для поиска продукта и, если они есть, срок годности и партия: в приходе срок подставляется сам, а партии с разными сроками попадают в разные строки.
- **Как работает.** Каждый скан добавляет единицу товара в документ. В инвентаризации штучный товар прибавляет единицу к посчитанному, а весовой и объёмный закрывает окно и ставит курсор в строку: его нужно взвесить. Код, который держат перед камерой, считается один раз; убрали и показали снова — второй раз. USB- и Bluetooth-сканеры работают без настройки, достаточно открыть окно сканера. Кода нет в номенклатуре, бот скажет об этом, а не выдумает продукт.
- **Камера.** Работает на защищённом адресе (https) или на localhost. Если камеры нет или доступ закрыт, можно ввести код вручную. Распознавание браузерное (BarcodeDetector, а где его нет, ZXing), кадры никуда не отправляются.
- **Без связи.** Приложение открывается без связи (service worker сохраняет оболочку), каталог продуктов с кодами хранится на устройстве, поэтому сканер узнаёт товар и без сети. Документы, оформленные без связи, ждут в очереди (значок «Очередь» в шапке) и уходят сами, когда связь вернётся, с тем же ключом идемпотентности: дубликатов не будет. Документ, который сервер не принял (например, срок уже истёк), остаётся в очереди с причиной. Инвентаризацию без связи сохранить нельзя, только пересчитать на странице. Каталог стирается при выходе из системы.
- **Проверка без телефона.** Откройте лист штрихкодов `docs/demo-barcodes.html` на втором экране и наведите камеру. Лист пересоздаётся командой `npm run barcodes -w @zapas/server`; штрихкоды демо-продуктов настоящие (верная контрольная цифра).

## Приход по накладной

В форме прихода кнопка «Загрузить накладную» принимает **УПД в XML** (формат ФНС, из ЭДО или 1С, в UTF-8 и windows-1251) и, если подключено, **фото накладной**. Строки попадают в форму прихода, а проверяет и проводит их человек.

- **Поставщик** находится по ИНН (его можно указать в справочнике поставщиков), иначе по названию без «ООО» и кавычек.
- **Продукт** для каждой строки ищется по штрихкоду из накладной (поле GTIN, код товара или код маркировки), затем по тому, как этого поставщика сопоставляли раньше, затем по названию. Если названия лишь похожи, строка помечена «проверьте». Единицы пересчитываются: граммы в килограммы, миллилитры в литры.
- **Срок годности и партия** берутся из накладной (дополнительные сведения строки или код маркировки), если поставщик их указал, иначе из карточки продукта.
- **Запоминание.** Выбор продукта для непонятной строки сохраняется для этого поставщика: в следующей накладной она найдётся сама.
- **Повтор.** Накладную того же поставщика с тем же номером программа помечает как уже оприходованную и просит подтверждение.
- **Фото.** Распознаёт Claude (Anthropic), поэтому включается только при `ANTHROPIC_API_KEY`; без ключа кнопки фото нет, УПД работает всегда. Картинка уходит в сервис распознавания и на сервере не сохраняется. Распознанное нужно сверить с бумагой.
- **Проверка.** Образец `docs/samples/upd-donskoy.xml` (его создаёт `npm run sample-upd -w @zapas/server`) показывает все способы сопоставления: по штрихкоду, по названию, с пересчётом единиц и строку без продукта.

## Заказы поставщикам

Раздел «Заказы» (менеджер и выше). В карточке продукта указывается **поставщик по умолчанию** и **фасовка** (кратность заказа: коробка яиц, ящик молока), в справочнике поставщиков **почта для заказов**, **срок поставки** и **минимальная сумма заказа**.

- **Что заказать.** По каждому поставщику и точке считается список: заказывается, если остатка (без просрочки, с учётом уже заказанного и не принятого) хватит меньше чем на срок поставки плюс сутки, либо остаток не больше минимального. Количество доводится до запаса на срок поставки плюс «дней покрытия» из параметров (по умолчанию 7) и округляется вверх до целого числа фасовок. Без измеренных продаж считается только по минимальному остатку. К каждой строке написана причина, при нехватке до минимального заказа поставщика есть предупреждение.
- **Черновик.** Кнопка «Создать черновик» берёт количества с сервера, дальше их можно править, добавлять и убирать продукты, указывать желаемую дату и комментарий. На одного поставщика и точку не больше одного черновика.
- **Отправка.** Решает человек. Заказ уходит письмом на почту поставщика (ответ придёт отправившему менеджеру), событием `order.sent` на подписанные вебхуки (для кабинета поставщика, EDI или своего сервиса, см. «Интеграции») и сообщением в Telegram. Если почты у поставщика нет или SMTP не настроен, заказ всё равно отмечается отправленным, причина видна в заказе, текст заказа копируется кнопкой, письмо можно отправить повторно. Автоматической отправки без проверки нет сознательно.
- **Автоматические черновики.** У поставщика можно включить «Каждое утро готовить черновик»: в час утренней сводки система собирает черновики и пишет в Telegram, что они готовы. Отправлять их всё равно нужно вручную.
- **Приём.** В форме прихода выберите «Принять по заказу»: строки заполнятся остатком к приёмке (цена из заказа, срок из карточки продукта), поставщик возьмётся из заказа, а принятое количество засчитается в заказ. Частично принятый заказ получает статус «Принят частично»; если поставщик больше ничего не привезёт, заказ закрывается кнопкой «Закрыть заказ», и недопоставка перестаёт считаться «в пути».
- **Настройка почты.** Задайте `SMTP_URL` (например, `smtps://логин:пароль@smtp.example.ru:465`) и `SMTP_FROM` (`Запас <zakaz@example.ru>`). Адрес сервера и пароль в журналы и ответы не попадают.
- **Проверка.** В демо-данных у продуктов уже указаны поставщики и фасовки, у «Молочного комбината» включены автоматические черновики: зайдите в «Заказы» менеджером.

## Интеграции: стоп-лист в доставку, iiko и 1С

Готовых сертифицированных коннекторов к iiko и 1С нет: «Запас» отдаёт и принимает данные через открытые форматы, на которые подключаются кассовая система, агрегатор доставки или посредник.

- **Вебхуки (Администрирование → Интеграции).** Адрес приёмника, события и точка. При любом изменении стоп-листа (закончился товар, истёк срок, ручной стоп, снятие) на адрес уходит `POST` с JSON: что добавилось, что ушло и полное состояние точки. Каждый запрос подписан (`X-Zapas-Signature`, HMAC-SHA256 от «время.тело» секретом адреса), у каждой доставки свой идентификатор. При сбое приёмника отправка повторяется через 30 секунд, 2 минуты, 10 минут, час и 6 часов, после пяти проваленных событий подряд адрес выключается сам. Есть кнопки «Проверить», «Отправить состояние» (полный срез при первом подключении) и журнал отправки. Секрет показывается один раз и меняется кнопкой.
- **Лента для кассы.** `GET /api/pos/stop-list` и `GET /api/pos/products` по тому же ключу кассы, что и продажи: касса сама забирает стоп-лист своей точки и каталог (артикул, штрихкод, цена).
- **Коды позиций.** Продукт узнаётся по артикулу и штрихкоду, блюдо по полю «Код в кассе» в карточке блюда (код блюда в iiko или 1С).
- **Импорт номенклатуры.** На странице «Номенклатура» кнопка «Импорт из CSV»: выгрузка из iiko, 1С или Excel (UTF-8 или Windows-1251, разделитель находится сам). Колонки распознаются по названию («Артикул» или «Код», «Наименование», «Группа», «Ед. изм.», «Цена», «Себестоимость», «Штрихкод»). Перед записью показывается, что создастся, что изменится и какие строки с ошибками; у существующего продукта меняется только указанное в файле, единица не меняется никогда.
- **Адреса приёмников.** По умолчанию разрешены только внешние https-адреса. Если приёмник стоит во внутренней сети (кассовый сервер в ресторане), администратор сервера включает `WEBHOOK_ALLOW_PRIVATE=true`.
- **Проверка.** `X-Zapas-Signature` проверяется так же, как в примере на вкладке «Интеграции». Для быстрой проверки поднимите любой локальный приёмник, включите `WEBHOOK_ALLOW_PRIVATE=true` и `WEBHOOK_ALLOW_HTTP=true`, создайте адрес и поставьте позицию в стоп-лист.

## ВСД «Меркурия» и марки «Честного знака»

В продукте отмечается, что он идёт с ветеринарным документом (молоко, мясо, рыба, яйцо) и/или маркируется (молочная продукция, вода). Тогда в строке прихода появляется поле номера ВСД, а сканер принимает код маркировки целиком.

- **ВСД.** Номер (UUID из «Меркурия») вводится в строке прихода или приходит из УПД (поле «Номер ВСД» в дополнительных сведениях строки). Срок на погашение 24 часа с приёмки. Раздел «Прослеживаемость» показывает документы, которые ждут погашения, просроченные подсвечены; кладовщик отмечает «Погашен в «Меркурии»», менеджер может вернуть отметку. Просрочка попадает в утреннюю сводку Telegram.
- **Марки.** Каждый отсканированный код DataMatrix добавляет единицу товара и сохраняется вместе с партией. Одна и та же марка дважды не принимается ни в форме, ни в базе (по GTIN и серийному номеру), марка другого товара отклоняется по GTIN. Вкладка «Марки» показывает партии с числом марок и сколько уже должно выбыть, менеджер выгружает реестр в CSV для сверки с личным кабинетом.
- **Что система не делает.** Обмена с «Меркурием» и ГИС МТ нет: Запас ведёт реестр и напоминает, а погашение ВСД и вывод марок из оборота выполняются в самих системах. Отметка «Погашен» это отметка человека, а не ответ государственной системы.
- **Проверка.** `npm run sample-upd -w @zapas/server` создаёт УПД, где у молока и кефира указаны номера ВСД, а у молока ещё и код маркировки; после загрузки они попадают в строки прихода.

## Бот в Telegram

Кроме уведомлений (утренняя сводка, новые позиции в стоп-листе) бот отвечает на команды. Чтобы им пользоваться:

1. Администратор создаёт бота у @BotFather и задаёт `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` (чат для рассылки).
2. Сотрудник открывает в веб-интерфейсе меню пользователя, выбирает «Telegram» и нажимает «Получить код».
3. Открывает бота по ссылке из окна (или пишет ему `/link КОД`). Код одноразовый и действует 10 минут.

Дальше бот отвечает с правами этого сотрудника: кладовщик видит только свои точки, менеджер все.

| Команда | Что делает |
|---|---|
| `/today` | сводка: просрочено, скоро истекает, стоп-лист, деньги под угрозой, главные действия |
| `/risks` | что списать, уценить, переместить |
| `/order` | что заказать |
| `/stoplist` | стоп-лист и блюда, которые скоро закончатся |
| `/stock молоко` | остатки продукта по точкам, сроки, пометка «ниже минимума» |
| `/expiring`, `/expired`, `/low` | скоро истекает, просрочено, ниже минимума |
| `/points`, `/whoami` | мои точки, под кем я вошёл |
| `/unlink` | отвязать чат |

К большинству команд можно добавить название точки: `/risks Центр`. Бот только показывает данные, ничего не меняет. Привязка снимается сама при смене или сбросе пароля и при отключении пользователя. Один токен опрашивает один экземпляр приложения: если запускаете несколько копий, на остальных задайте `TELEGRAM_COMMANDS=false`.

## Настройки сервера

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `DATABASE_URL` | подключение рабочей роли | обязательна |
| `MIGRATION_DATABASE_URL` | подключение владельца схемы | как `DATABASE_URL` |
| `JWT_SECRET` | подпись токенов, от 32 символов | обязательна |
| `BUSINESS_TZ` | часовой пояс бизнеса | `Europe/Moscow` |
| `COOKIE_SECURE` | флаг Secure у cookie сессии | `true` в production |
| `APP_ORIGINS` | допустимые источники браузерных запросов, через запятую | пусто (только свой домен) |
| `TRUST_PROXY` | откуда брать адрес клиента: `false`, число прыжков (`1` за одним прокси), список адресов прокси или `true` (доверять любому заголовку, небезопасно) | `false` |
| `WEB_DIST` | папка собранного интерфейса | не раздаётся |
| `RATE_LIMIT_MAX` | запросов в минуту с одного IP | `600` |
| `LOGIN_RATE_LIMIT_MAX` | попыток входа в минуту с одного IP | `10` |
| `ACCESS_TOKEN_TTL_SECONDS` | время жизни токена доступа | `900` |
| `REFRESH_TOKEN_TTL_DAYS` | время жизни сессии без активности | `14` |
| `SMTP_URL`, `SMTP_FROM` | почтовый сервер и адрес отправителя для писем поставщикам, задаются вместе; без них заказ отправляется без письма | отключено |
| `WEBHOOK_ALLOW_PRIVATE` | разрешить вебхуки на адреса во внутренней сети и на этом же компьютере | `false` |
| `WEBHOOK_ALLOW_HTTP` | разрешить вебхуки по http (без шифрования) | `true` вне production, в production `false` |
| `ANTHROPIC_API_KEY`, `INVOICE_MODEL` | распознавание фото накладной через Claude; без ключа выключено, модель по умолчанию `claude-opus-5-5` | выключено |
| `DB_POOL_MAX` | размер пула соединений с базой | `10` |
| `STOPLIST_SYNC_DELAY_MS` | через сколько после операции пересчитывается стоп-лист (частые операции склеиваются в один пересчёт) | `1500`, в тестах `0` |
| `SCHEDULER` | фоновые задачи: пересчёт стоп-листа раз в минуту, утренняя сводка в Telegram, очистка старых сессий | включён вне тестов |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | уведомления, задаются вместе | отключено |
| `TELEGRAM_COMMANDS` | бот отвечает на команды (опрос Telegram). Выключите на копиях, если токен опрашивает другой экземпляр | включено при заданном токене |
| `ENABLE_DOCS` | описание API на `/api/docs/openapi.json` (не в production) | `false` |

## Проверки

```bash
npm run typecheck        # строгая проверка типов во всех пакетах
npm test                 # модульные и интеграционные тесты
npm run audit:prod       # уязвимости в зависимостях, попадающих в продакшен
```

Серверные тесты идут на настоящей PostgreSQL, им нужна база `zapas_test` и файл `apps/server/.env.test` с её адресами. Покрыто: расход по срокам, атомарность документов, повторные запросы с одним ключом, двадцать параллельных продаж на остаток в десять, взаимные блокировки, инвентаризация, стоп-лист, рекомендации и прогноз, права и доступ к чужим объектам, вход и обновление сессии, заголовки безопасности, неизменяемость журналов, подмена записей аудита.

## Структура

```
apps/server     API на Fastify и PostgreSQL (маршруты → сервисы → чистая логика в domain/)
apps/web        интерфейс на React, TypeScript, SCSS
packages/shared схемы валидации, типы ответов, форматирование, политика паролей
docs/           архитектура, безопасность, описание API
docker/         инициализация ролей базы для docker compose
```

## Что не входит

Автоматическая отправка заказов без проверки человеком, электронный обмен заказами и накладными с поставщиками по EDI (событие `order.sent` позволяет подключить посредника), обмен с «Меркурием» и ГИС МТ (ВСД и марки ведутся в реестре, но в государственные системы не передаются), сертифицированные коннекторы iiko и 1С (обмен идёт через вебхуки, ленту по API-ключу и CSV-импорт), мобильное приложение.
