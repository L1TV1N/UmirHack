# Запас: архитектура

Система учёта остатков и сроков годности для общепита и розницы. Показывает, что лежит на складах и кухнях, что скоро испортится, какие позиции ушли в стоп-лист, и подсказывает, что продавать в первую очередь.

Документ описывает решение целиком: границы, данные, правила, API, безопасность, интерфейс. Если реализация расходится с документом, прав документ, расхождение считается багом.

## 1. Границы

В системе есть:

- несколько организаций, у каждой свои заведения (склады, рестораны, магазины, кафе, бары), сотрудники и справочники;
- номенклатура, категории, поставщики;
- партионный учёт: каждая поставка это партия со своим сроком годности и себестоимостью;
- журнал движения: приход, продажа, списание, перемещение, корректировка по инвентаризации;
- блюда с рецептурами (технологические карты), расход ингредиентов при продаже блюда;
- стоп-лист: автоматический (нет остатка, срок вышел, не хватает ингредиента) и ручной;
- прогноз скорости продаж и рекомендации: списать, дать скидку, переместить, продвигать через блюда, заказать;
- панель руководителя: деньги под угрозой, распределение по срокам, потери;
- роли (включая официанта) и права, привязка пользователей к заведениям, журнал аудита;
- заказы гостей от официантов со статусами, обращениями и переделкой за счёт заведения;
- кабинет поставщика «Отгрузка» с обменом заказами и статусами;
- интеграция с кассой по API-ключу, уведомления в Telegram, выгрузка отчётов в CSV.

Вне границ: бухгалтерия, налоги, обмен с государственными системами «Меркурий» и «Честный знак» (ВСД и марки ведутся в реестре), автоматическая отправка заказов без проверки человеком и электронный обмен с поставщиками по EDI и ЭДО (заказы поставщикам идут в собственный кабинет «Отгрузка» и письмом, событие `order.sent` оставляет точку подключения для чужих систем), мобильные приложения.

## 2. Допущения

Материалы кейса публикуются в день старта, поэтому решение построено по краткому описанию («учёт движения продуктов, контроль количества и сроков годности, формирование стоп-листа и рекомендаций по приоритетной продаже»). Допущения:

1. «Стоп-лист» понимается как в ресторанной автоматизации: список позиций и блюд, которые нельзя продавать сейчас.
2. Срок годности задаётся датой. Последний день продажи это дата срока включительно. Со следующих суток партия считается просроченной.
3. Единицы измерения: кг, л, шт. Количества хранятся с точностью до трёх знаков, деньги с точностью до копеек.
4. Часовой пояс бизнеса задаётся конфигурацией (по умолчанию Europe/Moscow), от него зависит, какой день считается «сегодня».

Один процесс API отдаёт и JSON, и статику фронтенда, поэтому одна точка входа, один origin, строгий CSP без внешних источников. Горизонтальное масштабирование возможно: сервер без состояния, всё состояние в PostgreSQL; планировщик защищён advisory-блокировкой, чтобы сводки не дублировались.

## 6. Модель данных

Идентификаторы `uuid`, кроме журналов (`bigint`). Даты сроков `date`, моменты событий `timestamptz`. Количества `numeric(14,3)`, деньги `numeric(14,2)`. Перечисления это `text` с `CHECK`.

**Доступ**
- `organizations`: организация; от неё зависят заведения, пользователи, справочники, настройки (ключ `app:<id>`), вебхуки, системы обмена и записи аудита (`audit_log.org_id`, в контрольную сумму не входит).
- `users`: организация `org_id`, email (уникален без учёта регистра), ФИО, `password_hash`, `role` (admin, manager, storekeeper, viewer, waiter), `must_change_password`, `is_active`, `failed_attempts`, `locked_until`, `password_changed_at`, `last_login_at`.
- `user_locations`: связь пользователя и заведений. Для admin и manager не нужна: они видят все заведения своей организации (список собирается при каждом запросе).
- `refresh_tokens`: хэш токена (SHA-256), `family_id`, `expires_at`, `revoked_at`, `replaced_by`, IP и user-agent.
- `api_keys`: хэш ключа, префикс для опознания, точка, `revoked_at`, `last_used_at`.

**Справочники**
- `locations`: организация, код (уникален внутри организации), название, вид (warehouse, kitchen, shop, cafe, bar), адрес, активность. Блюда готовят и продают на kitchen, cafe, bar (`servesDishes`).
- `categories`, `suppliers`: у каждой организации свои, артикулы, штрихкоды, названия и ИНН уникальны внутри организации.
- `guest_orders`, `guest_order_lines`, `guest_order_incidents`, `guest_order_events`: заказы гостей, строки с ценой на момент заказа, обращения (вид, виновный, решение, документ списания, потеря) и история.
- `purchase_order_events`: история заказа поставщику с пометкой, кто сделал (покупатель или кабинет).
- `products`: артикул (уникален), штрихкод (уникален, может быть пустым), название, категория, единица, `min_stock` (порог на точку), `shelf_life_days` (подсказка при приёмке), `price`, `cost`, `sellable`, `is_active`, `requires_vsd`, `requires_marking`.
- `dishes` и `dish_items`: блюдо, код в кассовой системе (уникален без учёта регистра), цена, ингредиенты с количеством на порцию.

**Учёт**
- `documents`: заголовок операции (receipt, sale, writeoff, transfer, inventory), номер, точка, автор, комментарий, `idempotency_key` (уникален в паре с автором).
- `batches`: продукт, точка, поставщик, дата приёмки, `expires_on`, `initial_qty`, `remaining_qty` (`CHECK >= 0`), `unit_cost`. Частичный индекс по `(product_id, location_id, expires_on)` для строк с остатком обслуживает выбор FEFO.
- `stock_movements`: журнал, только добавление. Партия, продукт, точка, тип, знаковое количество, снимок себестоимости, цена продажи, причина списания, блюдо (если расход через блюдо), документ, автор. Триггер запрещает `UPDATE` и `DELETE`, у прикладной роли отозваны эти права.
- `promotions`: скидка на партию (1–90%), срок действия, отмена. На партию одна активная акция (частичный уникальный индекс).
- `inventories` и `inventory_lines`: сессии инвентаризации, снимок ожидаемого и введённый факт.
- `webhook_endpoints`: адреса для событий (название, адрес, зашифрованный секрет, события, точка, состояние, серия неудач). `webhook_deliveries`: очередь и журнал отправки (событие, тело, статус, число попыток, время следующей попытки). `stoplist_published`: стоп-лист по точке, каким он был при прошлой публикации; разница с текущим и есть событие.
- `purchase_orders` и `purchase_order_lines`: заказы поставщикам (номер `ЗК-000001`, поставщик, точка, статус `draft`/`sent`/`partial`/`received`/`cancelled`, желаемая дата, сумма, кто и когда отправил, результат письма) и их строки (количество, цена, принятое количество). Уникальный индекс не даёт завести второй черновик на ту же пару поставщика и точки. У `suppliers` добавлены почта, срок поставки, минимальная сумма, признак автозаказа, у `products` поставщик по умолчанию и фасовка.
- `vet_certificates`: ВСД «Меркурия», привязан к партии: номер (UUID, уникален), точка, продукт, количество, `due_at` (приёмка плюс 24 часа), статус `pending`/`redeemed`, кто и когда отметил погашение, комментарий.
- `batch_marks`: коды маркировки партии, только добавление. GTIN, серийный номер (пара уникальна) и код без разделителей GS1.
- `stop_list_manual`: ручные записи (точка, продукт или блюдо, причина, срок).
- `stop_list_state`: текущее автоматическое состояние стоп-листа со временем начала. Нужно для «в стопе с…» и для уведомлений о переходах.

**Служебное**
- `settings`: ключ → JSON (порог «скоро истекает», окно прогноза, дней покрытия для заказа и др.).
- `audit_log`: журнал аудита, только добавление, с цепочкой хэшей (`prev_hash`, `hash`).
- `notification_log`: что и когда отправили, чтобы не слать дубли.

**Инварианты целостности**
1. Остаток партии не может быть отрицательным (`CHECK`) и всегда равен начальному количеству плюс сумма знаковых движений по партии. Проверяется тестом.
2. Движения и аудит нельзя изменить или удалить ни приложением, ни прикладной ролью БД.
3. Продажа никогда не берёт из просроченной партии.
4. Операция либо применяется целиком, либо не применяется (одна транзакция на документ).

## 7. Бизнес-правила

### 7.1 Сроки

`days_left = expires_on − сегодня` в часовом поясе бизнеса. Статусы партии:

| Статус | Условие |
|---|---|
| Просрочена | `days_left < 0` |
| Критично | `0 ≤ days_left ≤ critical_days` (по умолчанию 1) |
| Скоро истекает | `days_left ≤ expiring_soon_days` (по умолчанию 3) |
| В норме | иначе |

«Доступный остаток» это сумма остатков непросроченных партий. «Остаток на руках» включает просроченные партии, пока их не списали.

### 7.2 FEFO

Первой расходуется партия с ближайшим сроком. Порядок: `expires_on`, затем `received_on`, затем `id`. Внутри транзакции кандидаты выбираются `SELECT … FOR UPDATE`. Строки документа сортируются по идентификатору продукта до блокировки, поэтому два параллельных документа не уйдут в взаимную блокировку. Если доступного остатка не хватает, документ отклоняется целиком с перечнем нехватки. Частичной продажи нет.

### 7.3 Операции

- **Приход**: партия на строку, срок задаётся датой (или производством плюс срок годности продукта), дата в прошлом отклоняется, если не включён флаг приёмки уже просроченного товара (он нужен для учёта брака).
- **Продажа**: продукт расходуется по FEFO. Блюдо раскладывается по рецептуре на ингредиенты, каждый расходуется по FEFO. Цена строки берётся из карточки, для партии с активной акцией со скидкой, цена каждого движения фиксируется отдельно.
- **Списание**: причина обязательна (просрочка, порча, бой, недостача, прочее). Можно указать конкретную партию. «Списать всё просроченное» делает один документ.
- **Перемещение**: расход из точки-источника по FEFO (или из указанной партии) и создание партий в точке-получателе с теми же сроками и себестоимостью. Один документ, две стороны, одна транзакция.
- **Инвентаризация**: сессия фиксирует ожидаемое, пользователь вводит факт. При подтверждении недостача списывается по FEFO движениями `adjustment_out`, излишек оформляется новой партией с `adjustment_in` и сроком, который указал пользователь. Подтверждённую сессию изменить нельзя.

Все операции принимают заголовок `Idempotency-Key`. Повторный запрос с тем же ключом возвращает уже созданный документ, а не создаёт второй.

### 7.4 Стоп-лист

Автоматические причины, на каждую точку:

1. Продукт с признаком «продаётся», у которого на точке есть история партий, но доступный остаток равен нулю. Причина «нет в наличии» или «весь остаток просрочен».
2. Блюдо (для точек вида «кухня»), у которого хотя бы одного ингредиента не хватает на порцию. Причина содержит список недостающих ингредиентов.

Предупреждение (не стоп): блюдо, которого хватает на три порции или меньше.

Ручная запись добавляет позицию в стоп-лист вручную с причиной и необязательным сроком. Снять её может менеджер. Автоматическое состояние пересчитывается после каждой операции, меняющей остатки, и раз в минуту планировщиком. Переходы «вошёл в стоп» и «вышел из стопа» пишутся в `stop_list_state` и уходят в уведомления.

Пересчёт после операции идёт в фоне и склеивается: десяток продаж подряд даёт один проход через `STOPLIST_SYNC_DELAY_MS` (по умолчанию 1,5 с), а кассе не приходится ждать, пока по всей номенклатуре обновится стоп-лист. Страница стоп-листа и панель читают состояние по общему срезу данных (раздел 11), поэтому параллельные запросы делят один пересчёт, а запись состояния идёт под рекомендательной блокировкой БД. Устаревший срез не затирает состояние, уже записанное более свежим: у каждого среза есть порядковый номер, и по каждой точке запоминается, какой срез писал последним.

## 8. Прогноз и рекомендации

### 8.1 Скорость продаж

Расход продукта на точке считается по движениям `sale` и `transfer_out` за окно `forecast_window_days` (по умолчанию 28 суток). Расход через блюда входит в сумму, а перемещения наружу учитываются, чтобы у склада, который ничего не продаёт, а только отгружает, скорость не была нулевой. Списания и корректировки в расход не входят.

Скорость `v` (единиц в сутки) это взвешенное среднее суточных значений: последняя неделя весит вдвое больше остальных. Сегодняшний день не берётся, он не закончился. Дни до первой приёмки позиции на точке не считаются нулевыми, поэтому у новой позиции скорость не занижена.

Рядом считается уверенность `min(1, дней наблюдения / 14)`. Если она ниже 0,5 (меньше недели истории), прогнозу не верим и оцениваем риск только по сроку: под угрозой считается всё, что истекает в ближайшие три суток.

### 8.2 Что под угрозой

Для продукта на точке партии берутся в порядке FEFO. Пусть `cum` это сколько нужно продать, чтобы опустошить все предыдущие партии. Для партии `i` с остатком `r_i` и `d_i` днями до срока:

```
горизонт      = d_i + 1                      (сегодня считается полным днём)
успеем_продать = clamp(v * горизонт − cum, 0, r_i)
под_угрозой    = r_i − успеем_продать
cum           += r_i
```

Просроченная партия целиком считается потерей. Партии со сроком дальше 14 суток риском не считаются: прогноз на месяцы вперёд ничего не стоит, а у позиций с длинным сроком (крупы, масло) он даёт ложные тревоги. Деньги под угрозой это `под_угрозой × себестоимость`.

### 8.3 Рекомендации

| Тип | Когда | Что предлагается |
|---|---|---|
| Списать | Партия просрочена | Списать остаток, показать потерю |
| Скидка | Под угрозой > 0 и до срока не больше 7 суток | Процент по срочности: 0–1 сутки 50%, 2–3 суток 30%, 4–7 суток 15%. Если под угрозой меньше четверти партии, ступень ниже. Потолок: цена со скидкой не ниже себестоимости, кроме последних суток, когда лучше продать дешевле, чем списать |
| Переместить | До срока от 2 до 10 суток, а на другой точке продукт расходуется быстрее, чем лежит | Количество, которое точка успеет продать до срока, с учётом того, что уже решено отправить туда из других мест |
| Продвигать | Под угрозой ингредиент, который используют блюда кухни | Список блюд, которые можно приготовить из имеющегося, для блюда дня |
| Заказать | Остаток ниже порога или хватит меньше чем на 2 суток | Количество до `reorder_cover_days` суток продаж, срок исчерпания остатка |

Количество штучных товаров в рекомендациях округляется до целых штук, весовых до десятых. Если на партию уже действует акция не ниже рекомендуемой, скидка не предлагается. Рекомендации не хранятся, а считаются по текущим данным, поэтому не устаревают. Применение рекомендации это обычная операция (акция, списание, перемещение) через те же эндпоинты и с теми же проверками прав.

Приоритет: сначала просроченное, затем срочность (меньше дней), затем сумма под угрозой.

Ответ `GET /analytics/recommendations` имеет вид `{ items, counts, total }`: `counts` и `total` считаются по всем найденным рекомендациям, а в `items` отдаются самые приоритетные, не больше 500 (дальше человек всё равно не прочитает, а на больших данных список весил бы мегабайты). Тексты рекомендаций собираются лениво, только для попавших в список. Фильтр `type` отбирает 500 лучших внутри типа, поэтому вкладка любого типа показывает свои самые важные позиции, а счётчики на вкладках остаются полными. Для одной точки (`locationId`) счётчики считаются по тому, что попало в список.

### 8.4 Горячие предложения

Список блюд, продажу которых стоит стимулировать: чем дороже и ближе к концу срока то, что блюдо способно израсходовать, тем выше приоритет. Считается чистой функцией `domain/hot-dishes.ts` по тому же срезу данных, что и рекомендации, и не хранится. Только кухни; блюда и продукты из стоп-листа исключаются, блюдо, которое нельзя приготовить, тоже.

Для каждого ингредиента блюда на кухне берутся все партии со сроком до 7 суток по порядку FEFO. У каждой партии свои величины:

```
срочность   u = 1 / (1 + суток_до_срока / 2)       (1 в последний день, 0,67 за сутки, 0,5 за двое)
вероятность w = 0,3 + 0,7 · (под_угрозой / остаток) по прогнозу из 8.2, от 0,3 до 1
```

Блюдо способно продвинуть `push` порций. Если о продажах блюда ничего не известно (новое, меньше 30% от полной уверенности), потолок 24 порции. Если известно, `push = min(порций из остатков, max(4, ceil(порций_в_сутки · (1 + суток_до_ближайшей_партии))))`, но не больше 120: нельзя рассчитывать продать за два дня втрое больше, чем блюдо продаёт обычно. Порции блюда считаются из расхода ингредиентов под его именем (`stock_movements.dish_id`), по каждому ингредиенту выходит одно число, берётся середина.

Блюдо забирает `push · расход_на_порцию` ингредиента из партий по FEFO. Вклад ингредиента в деньгах:

```
c_i = Σ по партиям (забрано · себестоимость · w · u) / 300 ₽
приоритет = 100 · (1 − e^(−Σ c_i))
```

Деньги разных ингредиентов складываются, а в шкалу 0-100 приводятся плавно: около 63 набирается, когда «срочных» денег 300 ₽. Приоритет следует за тем, сколько денег блюдо способно спасти, а не за долей остатка: так блюдо, которое съест 1,5 кг говядины за 850 ₽, не проигрывает блюду, которое съест остаток зелени на 25 ₽. Повторяющаяся в рецептуре строка продукта считается один раз.

Ингредиент, который нужен нескольким блюдам, делится по очереди: на каждом шаге берётся блюдо, которому остаток нужнее всего сейчас, оно забирает своё, приоритеты остальных пересчитываются. Блюдо ниже 8 ничего не забирает и в список не попадает, а все следующие ещё слабее, поэтому раздача на нём останавливается. Для блюда отдаются причины (ингредиент, срок, остаток, расход на порцию, с кем делится) по убыванию вклада, главный ингредиент первым, число порций, которое нужно продать, и себестоимость того, что блюдо израсходует. Рекомендация «Продвигать» из 8.3 остаётся короткой подсказкой по продукту, горячие предложения это список по блюдам.

Проверка качества: `test/domain/hot-dishes-fuzz.test.ts` прогоняет сотни случайных кухонь и проверяет свойства (конечные числа, приоритет 8-100, остаток не обещан дважды, порядок входных данных не влияет, невыбранное блюдо ничего не отнимает, без конкурентов более срочный ингредиент не снижает приоритет). На тех же кухнях ранжирование сверялось с «оракулом» (сколько реально находящихся под угрозой денег блюдо способно спасти в одиночку): корреляция Спирмена выросла с 0,54 у прежней модели, считавшей долю остатка, до 0,80, а блюдо №1 из списка спасает 82% лучшего возможного вместо 66%.

### 8.5 Прогноз момента стоп-листа

Для каждого блюда кухни, которое пока готовится, считается, через сколько часов оно перестанет готовиться (`domain/stoplist-forecast.ts`). Для каждого ингредиента строится кривая годного остатка на неделю вперёд с шагом в час: партии расходуются по FEFO равномерно со скоростью продаж (с поправкой модели спроса), а остаток партии пропадает в конце суток её срока. Остановкой ингредиента считается первый час, когда остатка меньше, чем нужно на порцию. Блюдо останавливается по самому раннему ингредиенту, он же называется ограничивающим. Причина `expiry`, если в последний час перед остановкой истекла партия, иначе `depletion`.

Допущения: новые поставки и открытые заказы поставщикам не учитываются, расход равномерен в течение суток. Если по ингредиенту мало истории продаж (уверенность ниже 0,5), расход не предполагается и учитывается только срок годности. Результат показывается на странице стоп-листа и в команде `/stoplist` бота.

### 8.6 Дефицитные ингредиенты

Каждый пересчёт стоп-листа ведёт историю нехваток (`shortage_episodes`): продукт на точке считается дефицитным, пока он назван причиной остановки блюда или сам в стопе. Эпизод открывается при появлении и закрывается при исчезновении, не больше одного открытого на продукт и точку. Заказы, которые система отклонила из-за нехватки, пишутся в `sale_refusals` вместе с недостающими продуктами и суммой заказа. `GET /analytics/shortages` складывает их в рейтинг: сначала продукты, что дольше всех не давали готовить, затем по числу отклонённых заказов. Отказ записывается и для заказов с кассы (`POST /pos/sales`). Демо-данные содержат сценарий нехваток за месяц, чтобы рейтинг не был пустым в первый день, дальше история копится сама.

### 8.7 Уценка в кассу и «спасено»

Скидка действует на партию (`promotions`). Продажа берёт цену со скидкой у партии, с которой списывает, а касса узнаёт о ней двумя способами: в ленте `GET /pos/products` поле `markdown` показывает скидку на ближайшую по FEFO партию с остатком (`modules/promotions/markdown.ts`), а при создании и отмене скидки в той же транзакции в очередь вебхуков ставится событие `promotion.changed`. Отчёт `GET /analytics/rescued` складывает продажи товара (не блюд), которые прошли по партии с действовавшей на момент продажи скидкой: выручка, себестоимость (столько пропало бы при списании) и сколько стоила скидка против обычной цены. Учёт «до» и «после» отмены скидки идёт по времени документа.

### 8.8 Рейтинг поставщиков

`GET /analytics/suppliers` (`modules/analytics/suppliers.ts`, оценка в `domain/supplier-score.ts`) за период считает для каждого поставщика четыре величины. Выполнение заказов: сколько по стоимости привезли от заказанного, среди отправленных заказов, срок которых наступил или которые уже закрыты. Сроки: доля заказов, первый приход по которым (документ с `order_id`) пришёл не позже `expected_on`; не привезённый до сих пор считается опоздавшим. Свежесть: какая доля срока годности оставалась при приёмке, по стоимости. Качество: порча и бой по партиям поставщика к принятому по стоимости. Оценка это взвешенная сумма 35, 25, 20 и 20 процентов; свежесть от 80% срока и выше даёт полный балл, порча от 5% к принятому нулевой. Если какой-то составляющей нет (не было заказов), оценка делится на сумму весов остальных. Классы: A от 90, B от 80. Потери по причинам складываются по партиям поставщика за период (всех причин, а не только порчи); перемещения не считаются приёмкой.

### 8.9 Журнал HACCP

`modules/haccp` (чистая часть в `packages/shared/src/haccp.ts`). Контрольная точка (`haccp_points`) имеет границы температуры и частоту замеров. Замер (`haccp_readings`) хранит границы, действовавшие в момент записи, и признак «в норме», поэтому смена границ не переписывает историю. Корректирующее действие это отдельная запись (`haccp_actions`, одна на отклонение). Таблицы замеров, действий и осмотров входят в «только добавление»: прикладная роль не может менять и удалять их, ошибку исправляют новой записью. Просроченным замер считается, когда с последнего прошло больше `every_hours` (у точки без замеров отсчёт от создания). Отклонение и отказ при бракераже уходят в общий чат Telegram. Бракераж (`haccp_inspections`, одна запись на партию) нужен скоропортящемуся (срок хранения до 10 суток) и продукции с ветеринарным документом, принятой за последние три дня.

### 8.10 Telegram-ассистент

`modules/telegram`. `TelegramApi` умеет кнопки (`sendMessage` с рядами `InlineButton`, `editMessage`, `answerCallback`), бот принимает `callback_query`. Данные кнопки не длиннее 64 байт и разбираются строго (`actions.ts`): `cmd:<команда>` запускает команду без параметров из белого списка, `sub:<тема>` переключает подписку, `a:d:<партия>:<процент>` и `a:w:<партия>` просят подтверждение, `y:...` выполняет, `n` отменяет. Нажатие проходит те же проверки, что и сообщение (личный чат, привязанный сотрудник, его роль и точки), а действие повторно проверяется при выполнении: подделанная кнопка не даёт больше прав. Скидка и списание вызывают те же сервисы, что и веб (`promotions/service.ts`, `writeOff`), и пишутся в аудит с пометкой Telegram. Подписки (`telegram_links.topics`): `digest`, `stoplist`, `hot`. Планировщик в час сводки рассылает личные сводки каждому подписанному по его точкам (отметка `digest_user` в `notification_log` не даёт отправить дважды), а при появлении новых позиций стоп-листа сотрудники получают только то, что на их точках.

## 9. API

Префикс `/api`, формат JSON, ошибки в едином виде `{ "error": { "code", "message", "details?" }, "requestId" }`. Списки принимают `limit` (до 200) и `offset`. Подробные схемы тел запросов лежат в `packages/shared`, это единственный источник правды.

|---|---|---|
| Вход | `POST /auth/login`, `/auth/refresh`, `/auth/logout`, `GET /auth/me`, `POST /auth/change-password` | все |
| Пользователи | `GET/POST /users`, `PATCH /users/:id`, `PUT /users/:id/password`, `POST /users/:id/unlock` | admin |
| Точки | `GET /locations`, `POST/PATCH /locations` | чтение все, запись admin |
| Справочники | `/categories`, `/suppliers`, `/products` (GET, POST, PATCH) | чтение все, запись manager и выше |
| Блюда | `/dishes` (GET, POST, PATCH) | чтение все, запись manager и выше |
| Остатки | `GET /stock/summary`, `/stock/batches`, `/stock/batches/:id`, `/stock/movements` | все, в пределах доступных точек |
| Операции | `POST /documents/receipts`, `/sales`, `/writeoffs`, `/writeoffs/expired`, `/transfers`, `GET /documents`, `/documents/:id` | storekeeper и выше, в пределах точек |

### 9.1 Бот Telegram

`modules/telegram`: `api.ts` (клиент Bot API за интерфейсом `TelegramApi`, в тестах подменяется), `links.ts` (одноразовые коды и привязка чата к пользователю, таблицы `telegram_links` и `telegram_link_codes`), `commands.ts` (разбор и обработчики команд, они вызывают те же сервисы, что и маршруты API), `bot.ts` (`TelegramBot`: проверки чата и частоты, привязка, цикл опроса с нарастающей паузой при сбоях), `routes.ts` (статус, код, отвязка для веб-интерфейса). Сервер сам ходит в Telegram (`getUpdates`), публичный адрес не нужен. Подробности защиты в `docs/SECURITY.md`.

### 9.3 Заказы поставщикам

`modules/orders`: `suggest.ts` (расчёт: остаток без просрочки плюс заказанное и не принятое сравнивается со скоростью продаж за срок поставки плюс сутки и с минимальным остатком, количество доводится до запаса на срок поставки и «дни покрытия» из параметров и округляется вверх до фасовки; продукты без поставщика по умолчанию не считаются), `service.ts` (черновики, отправка, отмена, закрытие, привязка прихода, автоматические черновики), `routes.ts`, `text.ts` (текст заказа для человека), `mailer.ts` (`Mailer` за интерфейсом, `SmtpMailer` на nodemailer, в тестах `FakeMailer`). Отправка в одной транзакции меняет статус, пишет аудит и ставит событие `order.sent` в очередь вебхуков, письмо и сообщение в Telegram уходят после фиксации: их сбой заказ не отменяет, причина письма сохраняется в заказе. Приход по заказу (`orderId` в `receive()`) блокирует заказ, берёт поставщика из него, засчитывает принятое и пересчитывает статус (`partial` или `received`). Планировщик раз в сутки в час сводки собирает черновики по поставщикам с автозаказом, отметка в `notification_log` не даёт сделать это дважды.

### 9.2 Интеграции

`modules/integrations`: `service.ts` (публикация стоп-листа, очередь доставки, подпись, воркер), `sender.ts` (отправка за интерфейсом `WebhookSender`, в тестах подменяется), `guard.ts` (проверка адресов и поиск адреса при соединении), `routes.ts` (адреса, журнал, ленты для кассы). Публикация устроена как сравнение состояний, а не как перехват переходов: после каждого пересчёта стоп-листа (операции, ручные изменения, планировщик раз в минуту) текущий стоп-лист точки сравнивается с сохранённым в `stoplist_published`, и разница становится событием для подписчиков. Так не теряются ни автоматические стопы, ни ручные с истёкшим сроком, ни изменения при перезапуске сервера. Публикации идут под advisory-блокировкой, поэтому одну разницу не отправят дважды. Воркер раз в пять секунд берёт события, срок которых подошёл (с арендой на две минуты), и отправляет их вне транзакции. Без подписчиков публикация ничего не считает.

`modules/catalog/import.ts` (разбор CSV, распознавание колонок и кодировки, план: что создать, что изменить, что пропустить) и `import-routes.ts` (просмотр и запись одной транзакцией). Просмотр и запись используют один и тот же разбор, запись повторяет его под блокировкой.

## 10. Безопасность

Подробности и чек-лист проверок в `docs/SECURITY.md`. Принципы:

**Аутентификация**
- Пароли только Argon2id, параметры не ниже рекомендаций OWASP. Минимум 10 символов, запрет на пароли из списка распространённых и содержащие email.
- Токен доступа живёт 15 минут и хранится только в памяти страницы. Refresh-токен непрозрачный (256 бит случайных данных), хранится в БД как SHA-256, отдаётся в cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`.
- Refresh ротируется при каждом использовании. Повторное предъявление уже использованного токена означает кражу: вся цепочка (`family_id`) отзывается.
- Блокировка учётной записи после серии неудач (экспоненциально растущая пауза) и ограничение частоты по IP. Время ответа не зависит от существования пользователя (проверка против фиктивного хэша), текст ошибки одинаковый.
- Смена пароля отзывает все refresh-токены пользователя.

**Авторизация**
- Роли admin, manager, storekeeper, viewer, проверка на каждом маршруте по явному списку. Маршрут без объявленных прав не регистрируется (проверяется тестом).
- Объектный уровень: каждая выборка и каждая запись фильтруются по доступным точкам пользователя.
- API-ключ кассы привязан к одной точке и может только создавать продажи. Ключ показывается один раз, хранится в виде хэша.

**Данные и запросы**
- Все запросы параметризованы (Kysely), динамических SQL-строк с пользовательскими данными нет.
- Каждый вход проходит строгую схему Zod: лишние поля отклоняются, длины и диапазоны ограничены. Тело запроса не больше 256 КБ.
- Выгрузки CSV защищены от формульных инъекций: ячейки, начинающиеся с `=`, `+`, `-`, `@`, табуляции или возврата каретки, экранируются.
- Журнал движений и аудит неизменяемы (триггеры и права). Журнал аудита связан цепочкой хэшей, `GET /audit/verify` находит подмену.
- Прикладная роль БД без прав на схему и без `UPDATE/DELETE` на журналах.

**Транспорт и браузер**
- Заголовки через Helmet: строгий CSP (`default-src 'self'`, без `unsafe-inline`), HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'`, `Permissions-Policy`.
- CORS закрыт, разрешён только список из конфигурации. В разработке прокси Vite, CORS не нужен.
- Проверка заголовка `Origin` на запросах, меняющих состояние по cookie (refresh, logout).
- Ответы с персональными данными отдаются с `Cache-Control: no-store`.

**Эксплуатация**
- Секреты только из окружения, при запуске проверяются на длину и отсутствие значений по умолчанию. В режиме production сервер не стартует с неподходящей конфигурацией.
- Логи структурированные, из них вырезаются токены, cookie и пароли. Ошибки наружу без стека и деталей БД, с идентификатором запроса.
- Контейнер запускается не от root, файловая система только для чтения, healthcheck.
- Зависимости проверяются `npm audit`, версии зафиксированы lock-файлом.

## 11. Надёжность и конкурентность

- Одна транзакция на документ, блокировка строк партий `FOR UPDATE` в детерминированном порядке.
- Уровень изоляции `READ COMMITTED` достаточен, потому что остатки защищены блокировками и `CHECK`.
- Идемпотентность операций через `Idempotency-Key`: ключ привязан к пользователю и к отпечатку тела запроса, повтор с другими данными это конфликт `idempotency_conflict`.
- Взаимные блокировки и сбои сериализации (PostgreSQL 40P01, 40001) повторяются автоматически (`lib/retry.ts`). Нехватка соединений в пуле и тайм-аут запроса дают 503 с `Retry-After`, а не 500.
- **Кеш расчётов** (`lib/snapshot-cache.ts`, `modules/analytics/snapshot.ts`). Панель, стоп-лист и рекомендации строятся по одному срезу данных (партии, остатки, скорости продаж). Параллельные запросы делят одну загрузку. Любая запись пользователя сбрасывает кеш, и лёгкий срез пересобирается сразу, поэтому человек видит результат своей операции. Тяжёлые срезы (загрузка дольше 250 мс) пересобираются не чаще раза в две длительности загрузки, а читатели пока получают предыдущий срез. Продажи с кассы кеш не сбрасывают. Производные расчёты (стоп-лист, рекомендации, суммы панели) запоминаются по объекту среза, а мелкие запросы-агрегаты панели (потери и выручка за 30 суток) кешируются тем же механизмом. Скорость продаж считается в SQL одной строкой на позицию, а не по строке на каждые сутки.
- Нагрузочная проверка на 54 тыс. партий: продажа 10 мс, стоп-лист 20 мс, документы 20 мс, панель 150–200 мс; пачка из 300 одновременных запросов (продажи, панель, стоп-лист, рекомендации, остатки) обрабатывается за 3–4 секунды без отказов.
- Тест на гонку: двадцать параллельных продаж на остаток в десять единиц продают ровно десять.
- Корректное завершение: сервер перестаёт принимать запросы, дожидается текущих и закрывает пул.
- Планировщик (сводки, пересчёт стоп-листа, автосписание просроченного) берёт `pg_try_advisory_xact_lock`, на нескольких экземплярах работает один.
- **Живое обновление** (`lib/events.ts`, `modules/events`, `web/src/api/live.ts`). `GET /api/events` это поток Server-Sent Events: сервер сообщает «данные изменились», а интерфейс сам перечитывает остатки, стоп-лист, рекомендации и заказы обычными запросами, с теми же проверками прав. В событии нет данных, поэтому утечь через него нечему. Сигнал уходит при сбросе кеша расчётов (любая запись пользователя) и после фонового пересчёта стоп-листа (продажи с кассы). Частые изменения склеиваются в одно событие за 300 мс. Потоку нужен токен, а `EventSource` заголовка не умеет, поэтому клиент читает его потоковым `fetch`; поток живёт не дольше 14 минут (меньше срока токена), на пользователя не больше пяти. Обрыв клиент переживает переподключением и перечитыванием данных. Хаб событий хранится в памяти процесса: при нескольких экземплярах приложения событие дойдёт только до клиентов своего экземпляра (для этого понадобится `LISTEN/NOTIFY`), а при недоступности потока интерфейс остаётся на прежнем опросе. Остановка сервера закрывает потоки хуком `preClose`.

**Принципы**
- Рабочий инструмент для кладовщика и менеджера: плотные таблицы, цифры с табличным начертанием, быстрые фильтры, действия рядом с данными.

## 14. Развёртывание

- `docker-compose.yml`: PostgreSQL и приложение. При первом создании базы скрипт `docker/initdb/01-roles.sh` заводит две роли: владельца схемы (им применяются миграции) и рабочую роль приложения. Миграции выполняются при старте контейнера. Контейнер приложения работает не от root, с файловой системой только для чтения.
- Конфигурация через переменные окружения, шаблон в `.env.example`. Сервер не стартует с неподходящей конфигурацией.
- Для разработки: `npm run dev` поднимает API и Vite с прокси на `/api`.
- Демо-данные: `npm run seed` (в Docker: `docker compose --profile demo run --rm seed`). В режиме production загрузка отказывается работать.
- Сервер сам отдаёт собранный интерфейс (`WEB_DIST`), поэтому у приложения один адрес и один origin.

## 15. Развитие

Сертифицированные коннекторы iiko и 1С (сейчас обмен идёт через вебхуки со стоп-листом, ленту по ключу кассы, `POST /pos/sales` и CSV-импорт номенклатуры), электронный обмен накладными (ЭДО) и каталог с прайсом в кабинете поставщика, подтверждение почты и приглашения по письму, обмен с «Меркурием» и ГИС МТ (сейчас ВСД и марки ведутся в реестре, а гасит их человек), мобильное приложение для инвентаризации, общий склад ограничения частоты и событий для нескольких экземпляров приложения.

## Обмен с 1С и приём чеков касс

- **Выгрузка в учётные системы** (`modules/exchange`). При проведении прихода, списания, перемещения и инвентаризации в той же транзакции создаётся задание в `exchange_jobs`. Фоновый обработчик берёт задания с арендой, собирает документ 1С по профилю (`onec.ts`: имена объектов и реквизитов хранятся в `external_systems.profile`), отправляет по OData и записывает ключ документа в `external_refs`. Повторная выгрузка идёт методом PATCH по этому ключу, поэтому дублей нет. Продукты, поставщики и склады связываются с объектами 1С через `external_refs`; без связи задание получает статус `blocked` и список недостающего. Транспорт (`transport.ts`) подменяется в тестах, а имитация сервера 1С (`emulator/onec.ts`) используется и в тестах, и для показа.
- **Приём чеков** (`modules/pos`). Правила разбора (`rules.ts`) превращают JSON, XML или CSV в нормализованные чеки, пресеты вендоров лежат в `presets.ts`. Каждый чек пишется в `pos_inbox`; продажа проходит через обычный `sell` с идемпотентным ключом от кассы и номера чека, неизвестные позиции остаются в статусе `pending_match` и доигрываются после записи в `pos_code_map`.
- **Что не проверено на настоящих системах:** сервер 1С, живые кассы и вендорские форматы. Всё это покрыто тестами на имитациях и образцах.

## Организации, заказы гостей и кабинет поставщика

- **Организации** (`organizations`, колонка `org_id` у пользователей, заведений, справочников, настроек, вебхуков, систем обмена и аудита). Principal входящего пользователя несёт `orgId`, а список видимых заведений собирается при каждом запросе: у администратора и менеджера это все заведения организации, у остальных назначенные (`modules/users/users.ts`). Все справочные выборки и изменения фильтруются по `orgId` (`lib/scope.ts`: `orgOf`). Домен знает организацию заведения и блюда (`dishVisibleAt`), поэтому блюдо чужой организации не попадает в расчёты стоп-листа, горячих предложений, прогноза и рекомендаций, даже когда фоновый пересчёт идёт по всем заведениям сразу. Организация по умолчанию (`DEFAULT_ORG_ID`) принимает всё, что создано без явного указания, поэтому прежние данные и тесты остались валидными.
- **Роль официанта** стоит ниже наблюдателя (`ROLE_RANK.waiter = -1`): маршруты учёта закрыты, а его собственные (`asUser('waiter')`) открыты всем ролям, чтобы права по таблице маршрутов проверялись одним правилом. Внутри хендлеров официант ограничен своими заказами.
- **Заказ гостя** (`modules/guest-orders`). Создаётся без списания (статус «Принят»). «Взять в работу» вызывает обычный `sell` с идемпотентным ключом заказа: продукты расходуются по FEFO, при нехватке заказ остаётся принятым. Обращение (разбили, не донесли, жалоба) фиксируется с виновным; решение «переделать бесплатно» списывает рецептуру блюда документом списания (причина «бой») и добавляет в заказ строку с ценой 0, потеря считается по себестоимости партий. События пишутся в `guest_order_events` с порядком по счётчику.
- **Кабинет поставщика** (`apps/supplier`) отдельный процесс: Fastify, SQLite (`node:sqlite`), собственная регистрация по ИНН и сессии. С «Запасом» говорит только по HTTP с подписью: «Запас» отправляет заказ на `/api/gateway/orders` (`modules/supplier-portal`: `pushOrder` после отправки, смены статуса, прихода, отказа; сбой записывается в заказ, `schedulerTick` повторяет), кабинет отвечает статусами на `/api/supplier-gateway/status`, справляется об ИНН и запрашивает состояние заказа. Статус меняется в кабинете только после согласия «Запаса». Адресат определяется по ИНН поставщика, поэтому заказ, пришедший раньше регистрации, ждёт её.
